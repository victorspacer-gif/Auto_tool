⛁ CaveBot — Complete Guide

Waypoint navigation, monster targeting, image-based attack detection & looting

1. Overview

The CaveBot is a fully automated waypoint navigation system adapted from TibiaAuto12's CaveBotController. It walks your character through a pre-recorded sequence of positions on the minimap, waits at each stop for combat, and loots corpses — all without manual intervention.

It is the orchestrator for three companion services that work together:

  • CaveBot (this) — walks waypoints and manages the cycle
  • Chase Target — continuously targets monsters in the battle window
  • Auto Looter — right-clicks SQM positions to pick up loot

1.1 Architecture

Each service runs in its own daemon thread. The CaveBot worker follows a fixed 7-phase cycle per waypoint: 

┌─────────────────────────────────────────────────────────┐
│  1. Load script → find active waypoint                 │
│  2. Walk to waypoint  (image detection OR coordinates)  │
│  3. Stand still for N seconds                           │
│  4. Attack window  (image-based IsAttacking OR timing)  │
│     a. Wait for combat to start  (coloured border)      │
│     b. Wait for combat to end    (border disappears)    │
│  5. Loot SQM positions                                  │
│  6. Advance to next waypoint                            │
│  7. Loop back to start on completion                    │
└─────────────────────────────────────────────────────────┘

1.2 Waypoint Lifecycle

Each waypoint in a script has a status field: only the waypoint with status: true is the active one. The CaveBot walks to the active waypoint, then advances the active flag to the next slot. On completion, it wraps around to index 0.

💡 Key concept A script always has exactly one active waypoint. The UI shows the previous, current, and next waypoint in a navigation panel above the waypoint list.

3. Making Scripts

A CaveBot script is a JSON array of waypoints stored in scripts/<name>.json. Each waypoint tells the bot where to walk and what to do when it gets there.

3.1 Waypoint Fields

FieldTypeDescription
markstringName of the minimap mark image (e.g. "CheckMark", "Star"). Empty string for coordinates-only.
xintScreen X-coordinate of the waypoint on the minimap.
yintScreen Y-coordinate of the waypoint on the minimap.
typeintWaypoint action type: 1 Walk, 2 Rope, 3 Shovel.
statusbool | stringtrue = active waypoint, false = inactive. A script with no waypoints has "NotConfigured".

Example — 3-waypoint loop script:

  { "mark": "CheckMark", "x": 1280, "y": 440, "type": 1, "status": false },

]

3.4 Image Detection Setup

The most reliable way to navigate uses image detection. Here's how to set it up:

  1. Capture a minimap reference — Click 📸 Capture Ref, enter CenterButton as the name, then click on the "Center" text button at the top-left of your minimap. This gives the bot a fixed reference point.
  2. Auto-detect minimap — Click 🗺️ Detect Minimap Region. The bot finds the minimap using CenterButton, zoom buttons, or minimap border.
  3. Ensure mark images exist — The images/MapSettings/ folder must contain PNG files for the marks you use (e.g., Star.png, CheckMark.png). These are the minimap icons you place in-game.
  4. Enable Img Detect + Arrival Check — Both toggles should be ON for image-based navigation.
  5. Record waypoints — Select a mark name from the dropdown, ensure the minimap is configured, and click ➕ Add WP. The bot auto-detects the mark on the minimap via image matching (TibiaAuto12 behaviour) — no manual clicking needed. Falls back to manual position capture (move mouse → press hotkey) when image detection is unavailable.
💡 Two walking strategies The bot tries image detection first (find mark on minimap via OpenCV). If that fails after 3 retries, it falls back to coordinates (the x/y stored in the waypoint). Enable Debug mode to force arrow-key scrolling between retries.

3.5 Battle Window Setup

For image-based targeting and IsAttacking detection, you need a configured battle region:

  1. Capture a Battle reference — Click 📸 Capture Ref, enter Battle as the name, then click on the "Battle" title bar text of your battle window.
  2. Auto-detect battle window — Click 🗺️ Detect Battle Window. The bot calculates the full battle list region (~155x415 px) below the title bar.
  3. Verify the region — The status label shows the detected (left, top, width×height).

3.6 IsAttacking — 16-Image Border Analysis

This is the most significant feature. Instead of blindly waiting for a timer, the CaveBot now uses real-time border detection to know when combat starts and ends.

How it works

The bot captures the battle list region and runs OpenCV template matching against 16 border images — 4 sides (Left, Top, Right, Bottom) × 4 colour variants (Red, BlackRed, Pink, BlackPink). These are tiny border-edge strips (e.g. LeftRed.png is 3×23 px, TopRed.png is 24×2 px).

When the character is attacking, the battle window gets a coloured border. If all 4 sides of any colour variant match at ≥ precision, the border is present → character is attacking.

A positive match is then verified with VerifyAttacking.png (a 33×33 px corner section of the border) to filter out false positives from stray UI elements.

Attack window cycle in cavebot:

# Phase 4 — image-based (when battle_region configured):
# 1. wait_until_attacking(timeout=5s)
#    → polls is_attacking() every 150ms until border appears
#    → returns True if combat started
# 2. wait_until_not_attacking(timeout=20s)
#    → polls every 250ms until border disappears
#    → returns True if combat ended (monster killed)
# Falls back to timing when no battle_region or OpenCV
✅ This replaces the old timing-based window Previously, the cavebot just slept for max(2s, stand_seconds * 2) without any feedback from the game. Now it waits for actual combat and proceeds as soon as the monster dies.

3.7 Saving Your Script

Scripts are saved automatically to scripts/<name>.json when you add/remove/reorder waypoints. The JSON format is human-readable and can be edited with any text editor.

You can also save and load complete configurations via the Config tab (💾 Save JSON / 📂 Load), which preserves all bot state including cavebot scripts, chase target settings, looter positions, and global options.

4. Running

4.1 Companion Services

When you click ▶ Start CaveBot, it automatically starts:

  • Chase Target — if configured (has monster names + battle list X)
  • Auto Looter — if configured (has SQM positions)

Each companion also has its own Start/Stop button for manual control.

Recommended startup sequence:

  1. Configure and load a script
  2. Set Chase Target monsters + battle list X
  3. Configure Auto Looter SQM positions
  4. Click ▶ Start CaveBot

4.2 Troubleshooting

⚠️ "No target found in 5s — continuing" The border analysis couldn't detect combat starting. Check:
  • Battle region is properly detected
  • Monster name images exist in images/Targets/Names/
  • Chase Target is configured and started
  • Monsters are actually in range
⚠️ "Minimap not found" Auto-detection failed. Capture a CenterButton reference or use coordinate-based walking. You can also disable Img Detect to force coordinate mode.
⚠️ "Battle window not found" Capture a Battle reference image (📸 Capture Ref → "Battle"). The bot searches images/Reference/Battle.png first, then images/TibiaSettings/Battle.png.
❌ Chase Target: "Already attacking, skip" is_attacking() returned True, so the chase target service skipped re-targeting. This is normal behaviour — it means the border analysis is working correctly.

4.3 Best Practices

  • Use the smallest mark images possible — Larger templates are slower to match.
  • Keep Precision at 0.8 — Lower values cause false positives, higher values miss valid matches.
  • Stand seconds: Set to 1–2 seconds to give the game time to render the battle list before the attack window begins.
  • SQM positions: Record all 9 positions (8 around + character's own) for complete looting coverage.
  • Test with a single waypoint first — Verify walking, targeting, and looting before recording a full route.
  • Direct mode for AFK: Use direct input to avoid cursor conflicts while multitasking.
  • MonstersAttack images: If your client uses different border colours, capture new Left.png/Top.png/etc. for your colour variant.

5. Technical Reference

5.1 State Model

CaveBotState

{
  active: bool,                   // Service running?
  script_name: "string",          // Current script filename (no .json)
  stand_seconds: int,            // Pause after arrival (default: 1)
  walking_enabled: bool,          // Walk between waypoints?
  walk_for_debug: bool,           // Arrow-key scrolling between retries
  attack_players: bool,           // Target player characters?
  force_attack: bool,             // Attack even without right-click context
  follow_mode: bool,              // Click character after targeting
  monsters_to_attack: ["string"],  // Monster names from config
  attack_mode: "normal",          // normal | ... (future modes)
  skill_key: "f1",                // Attack skill hotkey
  looting_enabled: bool,           // Auto-loot after combat?
  image_detection_enabled: bool,    // Use OpenCV for waypoint detection?
  arrival_detection_enabled: bool,   // Confirm arrival before proceeding?
  image_detection_precision: 0.8,  // OpenCV confidence (0.5–1.0)
  map_region: (L, T, W, H),      // Minimap area on screen
  sqm_positions: [(x,y), ...],     // Loot click positions
  battle_list_x: int,              // X-position of battle list
}

ChaseTargetState

{
  active: bool,
  monster_names: ["string"],     // Up to 4 monster name images
  attack_key: "f1",             // Key to press before targeting
  scan_interval_ms: 300,         // Poll interval (min: 50ms)
  follow_mode: bool,
  attack_mode: "normal",
  image_targeting_enabled: bool,   // Use OpenCV for targeting?
  image_targeting_precision: 0.8,
  battle_region: (L,T,W,H),    // Battle list area for IsAttacking + image targeting
  battle_list_x: int,             // For key-press targeting
}

AutoLooterState

{
  active: bool,
  sqm_positions: [(x,y), ...],
  loot_delay_min_ms: 200,          // Min pause between cycles
  loot_delay_max_ms: 500,          // Max pause between cycles
  jitter: 3,                       // ±pixel jitter on click position
}
