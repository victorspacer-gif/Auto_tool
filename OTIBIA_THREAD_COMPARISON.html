OTibia_Bot vs Auto_tool

Thread scheduling, input coordination, and architectural lessons

This document compares the thread coordination systems of two MMORPG automation tools — Auto_tool (SystemMonitor) and a reference OTibia bot — and documents architectural lessons worth importing.

1. Thread Scheduling Overview

OTibia_Bot Lock-Based Priority
  • Two global threading.Lock() instances: walker_Lock + attack_Lock
  • Implicit priority: combat threads hold walker_Lock → walker yields
  • attack_Lock prevents spell/attack double-fire
  • Healer runs freely — no lock coordination needed
  • QThread daemon loops with self.running flags
  • No notion of FIFO — priority is encoded in which locks are held
Auto_tool FIFO ExecutionGate
  • ExecutionGate with threading.Condition + token-based queue
  • Strict FIFO: first to request gets exclusive input ownership
  • All services equally weighted — fair, no starvation
  • MouseGate thin wrapper for discoverability
  • Timeout-based acquisition with pause integration
  • No concept of priority — healer, walker, fishing all compete equally

2. OTibia_Bot Lock Priority Model (Detailed)

The Two-Tier Lock Pattern
# Addresses.py — global locks at module level
walker_Lock = threading.Lock()   # Combat holds → walker yields
attack_Lock = threading.Lock()   # Guards spell/attack to avoid double-fire

# TargetThread — combat acquires walker_Lock
while read_targeting_status() != 0:
    if not walker_Lock.locked():
        walker_Lock.acquire()    # Stop the walker while we fight!
    # ... attack, cast, loot corpse ...
if walker_Lock.locked():
    walker_Lock.release()         # Release so walker resumes

# WalkerThread — walker checks lock state
while walker_Lock.locked() and wpt_action != 4:
    QThread.msleep(200)            # Yield to combat threads

# SpellThread / HealThread — check attack_Lock
if not attack_Lock.locked():       # Don't cast if attack is in progress
    if attack_monster(data):
        press_hotkey(key)
Priority Tier Threads Lock Behaviour
Critical Healer (HealThread) Runs freely — no lock coordination. Always acts when HP/MP thresholds met.
High Target (TargetThread), Spell (SpellThread) Acquire walker_Lock to pause walker. Check attack_Lock before casting.
Normal Walker (WalkerThread) Checks walker_Lock.locked() in busy-wait loop. Yields to combat.
Low Hotkeys, SmartHotkeys, Looting No lock coordination needed — low-impact background tasks.

3. The New PriorityGate (Imported into Auto_tool)

NEW PriorityGate — Tiered Preemption Model

The PriorityGate generalizes OTibia_Bot's two-lock model into N explicit priority tiers with preemption:

class PriorityGate:
    CRITICAL = 0  # Healer — preempts everything
    HIGH     = 1  # Attack/Spell — preempts NORMAL/LOW
    NORMAL   = 2  # Walker/Fishing/Runes
    LOW      = 3  # AFK/Right-click

# Usage in any service:
cycle_locked = self.runtime.mouse.acquire(
    stop_event, priority=PriorityGate.CRITICAL, module_id="healer"
)

Key behaviours:

  • Within same priority: strict FIFO ordering
  • Higher priority arrives: current owner's stop_evt is set — preempted
  • Preempted service: naturally retries on next loop iteration
  • Backward compatible: all existing callers still work with FIFO mode (default)

Toggle in the Config Tab: 📋 FIFO ↔ ⚔️ Priority (healer > combat > walker > background)

Design Decision: The preemption mechanism uses stop_evt.set() instead of forcing a release. This means the preempted service's current action (a single click or keystroke) completes gracefully before the loop checks stop_evt.is_set() and releases the gate. This prevents mid-click corruption while still preempting within ~1 loop iteration.

4. Architectural Lessons Worth Importing

4.1 Stuck Detection + Obstacle Discovery

OTibia_Bot tracks previous position and detects when stuck for >0.4 seconds. The last target coordinate is added to a discovered_obstacles set, and the A* path is recalculated. This is shared between Walker and Target threads.

# OTibia_Bot — WalkerThread & TargetThread
previous_pos = (my_x, my_y, my_z)
stuck_timer = 0

# In main loop:
my_x, my_y, my_z = read_my_wpt()
if (my_x, my_y, my_z) == previous_pos:
    stuck_timer += sleep_value
    if stuck_timer > 400:  # 0.4 seconds
        self.discovered_obstacles.add(self.last_target_pos)
        stuck_timer = 0
else:
    previous_pos = (my_x, my_y, my_z)
    stuck_timer = 0

Auto_tool status: CaveBot has no stuck detection. The walker moves to waypoint coordinates and relies on arrival detection (image or timer). Gap identified.

4.2 A* Pathfinding with Dynamic Obstacles

OTibia_Bot has a full calculate_path_astar() function (Functions/PathfindingFunctions.py) that accepts a blacklist of tile coordinates. Both the Walker and Target threads feed discovered obstacles into the same pathfinder, enabling them to navigate around dynamic barriers.

# Both threads merge blacklist + discovered obstacles
blacklist_2d = {(bx, by) for bx, by, bz in blacklist if bz == z}
all_obstacles = self.discovered_obstacles | blacklist_2d
path = calculate_path_astar(x, y, target_x, target_y, all_obstacles)
if path:
    next_step = path[0]
    walk(x + next_step[0], y + next_step[1])  # Take one step

Auto_tool status: No pathfinding. Walk is InputRouter.tap_key direction presses. Gap identified.

4.3 One-Shot Looting (Target+Battle Drop Integration)

When targeting is active and a monster is killed, OTibia_Bot right-clicks the corpse SQM, waits for the container to open, then runs a one-shot looting thread to grab items. When targeting is off, looting runs continuously scanning the screen.

# In TargetThread after monster kill:
if open_corpse:
    QThread.msleep(random.randint(1000, 1500))
    mouse_function(corpse_x, corpse_y, option=1)   # Open corpse
    QThread.msleep(random.randint(300, 500))
    if self.loot_data:
        self.looting_thread = LootThread(self.loot_data, one_shot=True)
        self.looting_thread.start()

Auto_tool status: AutoLooter runs as a standalone service cycling SQM positions. No kill-event triggering. Gap identified.

4.4 Smart Hotkeys (Key-to-Screen Macros)

OTibia_Bot lets users bind an F-key to a screen coordinate with a mode: Crosshair (wherever cursor is), On Yourself (character centre), or On Target (relative to target position). When the key is pressed, the mouse automatically clicks the correct screen location.

if win32api.GetAsyncKeyState(vk_code) & 1:  # Key just pressed
    mouse_function(hotkey_x, hotkey_y, option=1)  # Use item
    if option == 'On Target':
        dx = (target_x - my_x) * square_size
        dy = (target_y - my_y) * square_size
        mouse_function(center_x + dx, center_y + dy, option=2)  # Click target
    elif option == 'On Yourself':
        mouse_function(center_x, center_y, option=2)
    elif option == 'With Crosshair':
        mouse_function(cursor_x, cursor_y, option=2)

Auto_tool status: Hotkey jobs only send key presses (no mouse coordination). Gap identified.

4.5 OCR Battle List Targeting

When the attack key is set to key 13 (OCR mode), the Target thread captures the battle list region, runs OCR, and clicks on monster names directly — no hotkey spam needed.

# scan_and_click_battle_list_ocr()
screenshot = capture.get_screenshot()
gray = cv.cvtColor(screenshot, cv.COLOR_BGR2GRAY)
_, thresh = cv.threshold(gray, 150, 255, cv.THRESH_BINARY_INV)
data = pytesseract.image_to_data(thresh, output_type=Output.DICT)
for i in range(n_boxes):
    if data['text'][i].strip().upper() in targets:
        click_x = bx + x + w//2
        click_y = by + y + h//2 - TITLE_BAR_OFFSET
        mouse_function(click_x, click_y, option=2)
        return

Auto_tool status: ChaseTarget has image-based targeting (OpenCV template matching) but no OCR-based text targeting. Gap identified — but image matching is arguably more reliable than OCR for game text.

6. Recommendations

✅ Done: PriorityGate imported from OTibia_Bot's lock-priority model into Auto_tool. Toggle available in Config tab.
🎯 High-Value Gaps (worth importing):
  1. A* Pathfinding + Obstacle Discovery — Most impactful for CaveBot. Would replace blind direction-tap walking with intelligent navigation that auto-adapts to blocked tiles.
  2. Stuck Detection — Low complexity, high value. Track previous position, flag obstacles, recalculate. Can be added to CaveBot worker in ~50 lines.
  3. Kill-Triggered Looting — Link AutoLooter to ChaseTarget kill events for efficient one-shot looting.
📊 Lower Priority (nice-to-have):
  • Smart Hotkeys — Requires global hotkey interception (already have pynput). Adds crosshair/self/target modes.
  • OCR Battle List — Already have image-based targeting which is more reliable. OCR adds fallback for text-only monster identification.
  • Per-Module Profiles — Current single-file config works well; per-module adds complexity without clear benefit.
